# Wear OS App (watch-android)

**Native Kotlin + Compose for Wear OS. There is no React Native, no JavaScript and no Expo module in
this folder** — exactly as [`targets/watch/`](../targets/watch/README.md) is pure Swift/SwiftUI. The
watch app runs no JS bundle, so Hermes, `runtimeVersion` and OTA updates are all irrelevant to it.

It is a **standalone Gradle project**: it has its own wrapper, its own version catalogue and its own
`settings.gradle.kts`, and it builds from this directory alone.

## The one thing to understand first: this is a separate APK

If you are arriving from the Apple Watch side of this repo, the instinct you have is wrong, and it is
wrong in a specific way worth spelling out.

| Concern            | watchOS (`targets/watch/`)                                          | Wear OS (here)                                   |
| ------------------ | ------------------------------------------------------------------- | ------------------------------------------------ |
| Native project     | **Generated** into the gitignored `ios/` by `@bacons/apple-targets` | **Standalone Gradle project**, self-contained    |
| Distribution       | **Embedded** in the iOS app bundle — one App Store binary           | **Separate APK**, uploaded independently to Play |
| Bundle identity    | `.watch` **suffix** → `com.iferoporefi.myloyaltycards.watch`        | **IDENTICAL** `com.iferoporefi.myloyaltycards`   |
| Build entry point  | `yarn watch:build` → `xcodebuild`                                   | `./gradlew` in this directory                    |
| Expo config plugin | Required (`@bacons/apple-targets`)                                  | **None, and none is possible**                   |

Apple embeds a watch app inside its iOS host bundle, so Epic 5 had to _generate_ that target on every
prebuild. **Wear OS works the opposite way.** Since Wear OS 2 a watch app is a separate APK, uploaded
and updated independently in the Play Console. There is nothing to embed.

This is not merely a design preference — AGP 9.0 **removed** embedded-Wear-app support (the old
`wearApp` configurations) outright. There is no supported way to embed a Wear APK any more.

Two consequences:

- **No config plugin is needed**, and there is no `@bacons/android-targets` equivalent to adopt.
- **Nothing here may be written into `android/`.** That directory is gitignored
  ([`.gitignore`](../.gitignore)) and fully regenerated by `expo prebuild`; anything placed there is
  destroyed on the next run. That is Story 16.7's lesson, and it generalises: _anything you put in
  `android/` is not yours to keep._

## Requirements

- **JDK 17.** AGP 9.3 requires it as a minimum, and the build sets `sourceCompatibility` /
  `targetCompatibility` to 17. Kotlin's `jvmTarget` is deliberately not set — with AGP's built-in
  Kotlin it defaults to `compileOptions.targetCompatibility`, so the two cannot drift.
- **Android SDK** with platform **API 36** and build-tools **36.0.0+**.
- **Android Studio** (any version shipping AGP 9.3 support) — optional; the wrapper builds without it.
- A **Wear OS emulator image** or a real watch for running. API 30 or higher.

Point the build at your SDK with either `ANDROID_HOME` / `ANDROID_SDK_ROOT`, or a `local.properties`
file in this directory (Android Studio writes one for you). **`local.properties` is gitignored and must
stay that way** — it is a machine-local path, not project config.

## Build and run

Everything below runs from **this directory**.

```bash
cd watch-android
```

### Build

```bash
./gradlew assembleDebug
```

The APK lands in `app/build/outputs/apk/debug/app-debug.apk`.

`./gradlew assembleRelease` also works and produces an **unsigned** APK — see
[Signing, Play and Asset Links](#signing-play-and-asset-links).

### Run on an emulator

Create a Wear OS AVD once (arm64 on Apple Silicon, x86_64 on Intel):

```bash
sdkmanager --install "system-images;android-30;android-wear;arm64-v8a"
```

```bash
avdmanager create avd -n wearos30_arm64 -k "system-images;android-30;android-wear;arm64-v8a" -d wearos_small_round
```

Boot it, then install and launch:

```bash
emulator -avd wearos30_arm64 -no-snapshot-load
```

```bash
./gradlew installDebug && adb shell am start -n com.iferoporefi.myloyaltycards/com.iferoporefi.myloyaltycards.wear.MainActivity
```

### Run on a real watch

Enable **Developer options** → **ADB debugging** → **Debug over Wi-Fi** on the watch, then
`adb connect <watch-ip>:<port>` and use the same `installDebug` command. Pairing the watch to a phone
is **not** required to install a debug build, but the app has nothing to show without it — see below.

### Lint

```bash
./gradlew lintDebug
```

Rules that are deliberately suppressed, each with its reasoning, live in [`app/lint.xml`](app/lint.xml).
One warning is left **unsuppressed on purpose** (the missing monochrome icon) — see
[Known gaps](#known-gaps).

## Architecture

```
watch-android/
├── settings.gradle.kts          ← standalone build; includes :app only
├── build.gradle.kts             ← plugins, declared `apply false`
├── gradle.properties
├── gradle/
│   ├── libs.versions.toml       ← every dependency version, with its constraints
│   └── wrapper/                 ← tracked; pins the Gradle distribution + its SHA-256
├── gradlew / gradlew.bat        ← tracked
└── app/
    ├── build.gradle.kts
    ├── lint.xml
    ├── proguard-rules.pro
    └── src/main/
        ├── AndroidManifest.xml
        ├── kotlin/com/iferoporefi/myloyaltycards/wear/
        │   ├── MainActivity.kt
        │   └── presentation/WearApp.kt   ← placeholder screen; Story 10-3 replaces it
        └── res/
```

`namespace` is `com.iferoporefi.myloyaltycards.wear` (the code/R-class package) while `applicationId`
is `com.iferoporefi.myloyaltycards` (the identity Play sees). That split is deliberate: the sources
stay clearly namespaced without changing the application ID, which is not free to change.

## The three non-negotiable platform constraints

These are platform requirements, not preferences. Getting any of them wrong breaks Play association or
the Wearable Data Layer.

1. **`applicationId` is identical to the phone app** — `com.iferoporefi.myloyaltycards`, with **no
   suffix**. Play associates the watch APK with the phone app by application ID, and the Data Layer
   will not connect two APKs with different IDs. This deliberately **overrides** the instinct carried
   over from `targets/watch/expo-target.config.js`, which suffixes the watchOS bundle ID with
   `.watch`. Cross-check against `expo.android.package` in [`app.json`](../app.json) rather than
   typing it from memory.
2. **Same signing key as the phone app.** The Data Layer will not connect two APKs signed with
   different keys, and Play rejects the association.
3. **A Digital Asset Links entry for the Wear OS app**, carrying the `applicationId` plus the
   **SHA-256 hash of the signing certificate**, so the watch app is associated with the other versions
   of the app.

## Signing, Play and Asset Links

**Documented here, not configured here.** The release keystore, the Play Console setup and the Asset
Links publication are **@ifero's**, and no keystore, signing secret or `local.properties` is committed
to this repo. `assembleRelease` therefore produces an unsigned APK; that is expected.

### versionCode bands

Play allocates `versionCode` **per application ID**, and this Wear APK shares
`com.iferoporefi.myloyaltycards` with the phone app. It is therefore a **third consumer of one shared
counter space**. Story 16.7 exists because two counters already collided there.

| Band        | Consumer          | Set by                                                                                       |
| ----------- | ----------------- | -------------------------------------------------------------------------------------------- |
| `0`         | phone, alpha/beta | `beta-releases.yml` — bare `GITHUB_RUN_NUMBER`                                               |
| `1_000_000` | phone, production | `store-upload.yml` — `PRODUCTION_VERSION_CODE_OFFSET` in [`app.config.ts`](../app.config.ts) |
| `2_000_000` | **Wear OS APK**   | [`app/build.gradle.kts`](app/build.gradle.kts) in this project                               |

The Wear counter comes from the `WEAR_VERSION_CODE` environment variable — a **distinct name** from the
phone's `ANDROID_VERSION_CODE`, so a Wear build can never silently inherit the phone's counter.

Its contract is deliberately asymmetric, and the asymmetry is the point:

| `WEAR_VERSION_CODE`                  | Result                                                           |
| ------------------------------------ | ---------------------------------------------------------------- |
| unset                                | `versionCode` = `2000000` (the bare band) — the local-build case |
| a positive integer                   | `versionCode` = `2000000 + n`                                    |
| empty / `0` / negative / non-numeric | **the build fails**                                              |

Falling back on a _present but unusable_ value would emit a plausible-looking `versionCode`
indistinguishable from a legitimate first upload — the exact failure Story 16.7 documents. An unset
GitHub Actions variable interpolates to the empty string, so that case is a hard failure too. The sum
is computed in `Long` and checked against Play's maximum (`2_100_000_000`) before narrowing, so a
large counter cannot overflow into a negative `versionCode`.

This is set in **this project's own Gradle build, not in `app.config.ts`**: the two projects share no
build system, and coupling them would drag the Wear APK back into the "regenerated by prebuild" trap.

## Behaviour constraints inherited by Stories 10-2 … 10-6

- **Companion-only / non-standalone.** `AndroidManifest.xml` declares
  `com.google.android.wearable.standalone` = `false`, with the rationale inline. The app has no
  account, no card editor and no network path of its own, so without a paired phone it can never
  obtain a card. The accepted consequence is that Play surfaces it only to users with a compatible
  paired phone.
- **READ-ONLY for card data.** The single ratified exception is the `CARD_USED` usage event
  (ADR-2026-06-09-001, [`docs/adr-2026-06-09-watch-usage-events.md`](../docs/adr-2026-06-09-watch-usage-events.md)).
  Do not add a second write path.
- **Dates are strings.** Per `docs/project-context.md`'s Watch App Rules, store dates as strings and
  parse only for display; the phone sends ISO-8601 UTC with milliseconds. No `Date`-typed placeholder
  model exists here for 10-5 to undo.

## Toolchain

Recorded rather than pinned by prose — bump deliberately in
[`gradle/libs.versions.toml`](gradle/libs.versions.toml) and re-run `./gradlew assembleDebug`.

| Component             | Version                                                                                             |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| JDK                   | 17                                                                                                  |
| Gradle                | 9.6.1 (wrapper pins the distribution SHA-256)                                                       |
| Android Gradle Plugin | 9.3.1                                                                                               |
| Kotlin                | 2.4.10 (drives AGP's built-in Kotlin **and** Compose)                                               |
| Compose BOM           | 2026.06.01                                                                                          |
| Compose for Wear OS   | 1.6.2 (`compose-material3`, `compose-foundation`)                                                   |
| `compileSdk`          | 36                                                                                                  |
| `minSdk`              | 30 — Wear OS 3 floor and Play's Wear quality requirement                                            |
| `targetSdk`           | 35 — Play's 2026 rule is API 36, but Wear OS and Android Automotive are explicitly carved out at 35 |

Two toolchain facts that are easy to get wrong:

- **There is no `org.jetbrains.kotlin.android` plugin.** AGP 9 ships built-in Kotlin support and
  enables it by default. The Compose compiler plugin is still applied separately, and its version _is_
  the Kotlin version — so the single `kotlin` entry in the version catalogue drives both.
- **`compileSdk` stays at 36** although AGP 9.3 supports API 37. 36 is what the phone app's Expo SDK
  compiles against and what CI runners provide out of the box; moving to 37 means installing a
  platform on every machine and in CI for no current benefit.

## CI

[`.github/workflows/wear-os-build.yml`](../.github/workflows/wear-os-build.yml) runs
`./gradlew assembleDebug`, path-filtered to `watch-android/**` so it stays off the phone app's critical
path — the same shape as `chromatic.yml`'s filtering and `watchos-tests.yml`'s scoping.

**Be precise about what that does and does not prove**, because an absent job is easily mistaken for
coverage:

- ✅ **Compiles.** The module cannot rot silently; a broken build fails the PR that broke it.
- ❌ **No unit tests run** — there are none. This story is a scaffold with no logic worth testing, and
  manufacturing tests for a placeholder would be worse than having none. Stories 10-2 onward carry real
  testable logic and should add them.
- ❌ **No lint in CI.** `./gradlew lintDebug` passes locally and is worth wiring up once the module has
  real code; it is not a gate today.
- ❌ **No instrumented or on-device test.** The APK's install-and-launch was verified by hand on a Wear
  OS 3 (API 30) emulator, not by CI.

`ci-quality-gates.yml` is untouched and does **not** compile Kotlin as a side effect: `yarn lint` is
`eslint . --ext .ts,.tsx`, and `jest.config.js` matches only `**/*.test.[jt]s?(x)` — `.kt` files are
invisible to both. Prettier does read this README (it reads `.gitignore`, which excludes only build
output here).

## Known gaps

Flagged rather than silently carried:

- **No monochrome launcher icon**, so no themed icon on Android 13+. Adding one needs a flat silhouette
  asset that does not exist in this repo — a design task, not a code one. Lint's
  `MonochromeLauncherIcon` warning is left **unsuppressed** so it stays visible.
- **The launcher icon is a copy, not a reference.** `app/src/main/res/mipmap-*/ic_launcher_foreground.png`
  is a faithful downscale of `assets/adaptive-icon.png` and the background colour matches
  `expo.android.adaptiveIcon.backgroundColor`, but **nothing keeps them in sync**. A standalone Gradle
  project cannot reach into the JS app's assets without giving up being self-contained. If the phone
  icon changes, this one must be regenerated by hand.
- **No production telemetry.** Sentry has effectively no Android coverage (~10 events / 90 days, ~100 %
  iOS), so nothing about this app will be observable in production at launch. "No crash in Sentry"
  proves nothing here.
- **No Wear OS complication.** The Epic 5 generic-complication follow-up was parked into Epic 10 but has
  no story number yet. Note that a complication is also the only surface that would need brand artwork —
  the card list renders initials on a coloured circle, so Epic 10 as scoped needs no Wear drawable
  pipeline.
- **No Fastlane lane for the watch APK.** `fastlane/Fastfile`'s `platform :android` lanes cover the
  phone app only. Extending them is release plumbing, best done once there is something worth shipping.

## Scope

This story (10.1) delivers the module, the build and a placeholder screen — nothing else.

| Owned by | Work                                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| **10-2** | Brand catalogue generation                                                                                  |
| **10-3** | Card list UI, favourite indicator, persisted sort (Epic 9 parity)                                           |
| **10-4** | Barcode rendering                                                                                           |
| **10-5** | Room storage — owns the schema, hence **no Room dependency here**                                           |
| **10-6** | Data Layer sync and `CARD_USED` — the **only** consumer of the declared `play-services-wearable` dependency |

The Play Services Wearable dependency is declared but **unused**, purely so 10-6 can wire sync without
editing build files. Do not add sync logic before then.
