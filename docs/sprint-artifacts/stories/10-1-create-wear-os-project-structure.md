# Story 10.1: Create Wear OS project structure [Enabling]

Status: review

Epic: 10 — Wear OS App

> **Gates run inside a `.claude` worktree too, once you `yarn install` there.** `jest.config.js`
> anchors its `.claude` ignore patterns to `<rootDir>`, so a worktree runs its own suite instead of
> finding zero tests. A worktree with no `node_modules` fails on missing dependencies instead — a
> different problem. Native builds (`yarn watch:build`, `./gradlew`) still need the **main checkout**:
> `ios/`, `android/` and `.expo/` are gitignored and absent in a fresh worktree. `--no-verify` stays
> forbidden either way.
>
> **This is the enabling story for all of Epic 10.** 10-2 … 10-6 build directly on the module layout,
> `applicationId` and Gradle setup decided here. Get the Open Decisions right; they are binding.
>
> **`android/` is gitignored** (`.gitignore:52-53`) and regenerated by `expo prebuild`. **Nothing in
> this story may write into it.** See [Why this cannot mirror watchOS](#why-this-cannot-mirror-watchos).
>
> **No React Native, no JS, no Expo module in `watch-android/`.** Pure Kotlin + Compose for Wear OS,
> exactly as `watch-ios/` + `targets/watch/` are pure Swift/SwiftUI.

## Story

As a developer,
I want a properly structured Wear OS project in the repo,
so that I can build, test and release the Android watch companion app without fighting the phone
app's native build.

## Context

### What exists to mirror

Epic 5 delivered the Apple Watch app, and its structure is the model — but only partly, and the
differences are the whole substance of this story.

| Concern           | watchOS (shipped)                                               | Wear OS (this story)                           |
| ----------------- | --------------------------------------------------------------- | ---------------------------------------------- |
| Source location   | `targets/watch/` (Swift) + `watch-ios/` (scripts/tests)         | `watch-android/` (per Epic 10 AC1)             |
| Native project    | **Generated** into gitignored `ios/` by `@bacons/apple-targets` | **Standalone Gradle project**, self-contained  |
| Bundle identity   | `.watch` **suffix** → `com.iferoporefi.myloyaltycards.watch`    | **IDENTICAL** `com.iferoporefi.myloyaltycards` |
| Distribution      | **Embedded** in the iOS app bundle, one App Store binary        | **Separate APK**, uploaded independently       |
| Build entry point | `yarn watch:build` → `xcodebuild` on the generated workspace    | `watch-android/gradlew`                        |
| Generated code    | `targets/watch/Generated/`, `watch-ios/Generated/` gitignored   | gitignored, per 10-2                           |

### Why this cannot mirror watchOS

The watchOS app is a **target inside the phone app's Xcode project**. It has to be, because Apple
ships a watch app embedded in its iOS host bundle. Since `ios/` is gitignored, Epic 5 needed
`@bacons/apple-targets` to _generate_ that target from `targets/watch/expo-target.config.js` on every
prebuild.

**Wear OS works the opposite way.** Since Wear OS 2, a watch app is a **separate APK, uploaded and
updated independently in the Play Console** — there is no embedding. So `watch-android/` does not need
to be injected into the generated `android/` project at all, and **must not be**: anything written
into `android/` is destroyed by the next `expo prebuild`.

**Consequence: no config plugin is needed for this story.** That is the single most important
difference from Epic 5, and it makes 10-1 _cheaper_ than 5-1 was, not more expensive. There is no
`@bacons/android-targets` equivalent to adopt, and none is required.

### The three platform constraints that are not negotiable

1. **`applicationId` must be identical to the phone app** — `com.iferoporefi.myloyaltycards`
   (`app.json` `expo.android.package`). This is required for Play to associate the watch APK with the
   phone app and for the Wearable Data Layer to connect the two. **This breaks the watchOS mental
   model**, where the watch target is deliberately suffixed `.watch`. Do not add a suffix here.
2. **Same signing key as the phone app.** The Data Layer will not connect two APKs signed with
   different keys, and Play rejects the association.
3. **Digital Asset Links** must carry an entry for the Wear OS app (the `applicationId` plus the
   SHA-256 hash of the signing certificate) so the watch app is associated with the other versions of
   the app.

### Versions — verified, not guessed

- **`minSdk = 30`** (Android 11). This is the Wear OS 3 floor and matches Epic 10's AC ("Wear OS 3+
  (API 30+)"). It is also Play's long-standing Wear OS app-quality requirement.
- **`targetSdk = 35`** (Android 15). Play's 2026 requirement is API 36 for phone apps but **Wear OS
  and Android Automotive are explicitly carved out at API 35** for new submissions. Existing Wear OS
  apps must be on API 34+ by 2026-08-31; since this app is new, go straight to 35 and skip that
  deadline entirely.
- **`compileSdk` ≥ `targetSdk`.**
- **AGP / Gradle / Kotlin / Compose-for-Wear-OS versions are NOT pinned by this story.** Use the
  current stable set that Android Studio scaffolds, then **record the exact versions in the Dev Agent
  Record**. Pinning numbers in a story written before implementation is how stale-by-arrival happens;
  the constraint is `minSdk 30` / `targetSdk 35`, not a toolchain snapshot. Compose for Wear OS
  requires `minSdk` ≥ 25, so 30 is comfortably clear.

### Interaction with the phone app's Android build

- **`versionCode` collision risk (Story 16.7).** `app.config.ts` computes the phone app's Android
  `versionCode` from `ANDROID_VERSION_CODE` (CI: `GITHUB_RUN_NUMBER`), with
  `PRODUCTION_VERSION_CODE_OFFSET = 1_000_000` carving production into its own band so the
  `beta-releases.yml` and `store-upload.yml` counters cannot collide _in Play's single shared
  versionCode space_. **The Wear OS APK is a third consumer of that same space.** It needs its own
  band; see Open Decision 4. Getting this wrong reproduces exactly the "Version code 1 has already
  been used" failure that Story 16.7 existed to fix.
- **No change to `app.json`, `app.config.ts`, or any Expo plugin.** This story adds a sibling Gradle
  project; it does not touch the React Native app's configuration. If you find yourself editing
  `app.json`, stop — you have taken the watchOS-shaped path.
- **Not an OTA concern at all.** `watch-android/` ships no JS, so `runtimeVersion` and the
  `appVersion` policy are irrelevant to it.

## Acceptance Criteria

**AC1 — `watch-android/` exists as a self-contained Gradle project.**
`watch-android/` at repo root contains a native Kotlin + Compose for Wear OS project with its own
Gradle wrapper, buildable from that directory alone. It contains **no** React Native, JS, or Expo
code. It does **not** reference, read from, or write into `android/` or `ios/`.

**AC2 — Build configuration is correct and verified.**
`minSdk = 30`, `targetSdk = 35`, `compileSdk ≥ targetSdk`; `applicationId` is exactly
`com.iferoporefi.myloyaltycards` with **no suffix**; the module declares itself a Wear OS app. The
exact AGP / Gradle / Kotlin / Compose-BOM versions used are recorded in the Dev Agent Record.

**AC3 — The project builds and launches.**
`./gradlew assembleDebug` succeeds from `watch-android/`, and the resulting APK installs and launches
on a Wear OS emulator (API 30 or higher) showing a placeholder screen. No manual fixes needed after
checkout.

**AC4 — Standalone/non-standalone is declared explicitly.**
`AndroidManifest.xml` carries the `com.google.android.wearable.standalone` meta-data with an explicit
value and an inline comment justifying it. This app is **non-standalone** (`false`) — it is
companion-only and read-only for card data, exactly as the watchOS app is, and it has no way to obtain
cards without a paired phone. See Open Decision 2.

**AC5 — Wearable Data Layer dependency is present but unused.**
The Play Services Wearable dependency is declared so 10-6 can wire sync without touching the build
files, and a short comment records that 10-6 owns its use. No sync logic in this story.

**AC6 — `watch-android/README.md` documents the module.**
It must state: this is **native Kotlin/Compose, not React Native**; the JDK/Android Studio/SDK
requirements; how to build and run on an emulator and a real watch; that it is a **separate APK** from
the phone app, not embedded; that `applicationId` is deliberately identical to the phone app and why;
that it is companion-only and **read-only for card data** (usage events excepted, per
ADR-2026-06-09-001); and how it relates to `watch-ios/` + `targets/watch/`. Mirror the intent of
`targets/watch/README.md`.

**AC7 — Gitignore is correct.**
`.gitignore` excludes Gradle/Android build output under `watch-android/` (`build/`, `.gradle/`,
`local.properties`, `*.apk`, `*.aab`) **and nothing else** — the Gradle wrapper (`gradlew`,
`gradlew.bat`, `gradle/wrapper/*`) and all sources stay tracked. Follow the shape of the existing
watchOS block (`.gitignore:73-78`), which excludes only build artifacts and keeps sources.
`watch-android/Generated/` is 10-2's concern, not this story's.

**AC8 — CI is not broken and not silently skipped.**
The existing workflows stay green. Whether Wear OS gets its own CI job is **Open Decision 5**; if the
answer is "later", say so explicitly in the README rather than leaving the absence of a job to be
mistaken for coverage. `ci-quality-gates.yml` must not start compiling Kotlin as a side effect.

**AC9 — Signing, Play and Asset Links are documented, not configured.**
The README records the three non-negotiable constraints (identical `applicationId`, same signing key,
Digital Asset Links entry with `applicationId` + signing SHA-256) and the `versionCode` band decision
from Open Decision 4. **Actual keystore material and Play setup are @ifero's** — do not commit
secrets, keystores, or a `local.properties`.

**AC10 — No regression to the phone app.**
`yarn lint`, `yarn typecheck`, `yarn test`, `yarn tokens:check`, `yarn splash:check` all pass from the
main checkout; `yarn watch:build` (watchOS) still succeeds. Adding a sibling Gradle project must not
perturb any of them.

### Latest technical information

- **Play target API, 2026:** new submissions must target API 36 (Android 16) **except Wear OS and
  Android Automotive, which must target API 35 (Android 15) or higher**. Existing Wear OS apps must
  reach API 34+ by 2026-08-31, with extensions available to 2026-11-01. A new app going straight to 35

## Open Decisions — binding defaults, implement as written

1. **`watch-android/` is a standalone Gradle project with its own wrapper — no Expo config plugin, no
   entry in the generated `android/` project.** Rationale: Wear OS apps ship as separate APKs, and
   anything in `android/` is destroyed by `expo prebuild`. This is the inverse of the watchOS setup and
   is the correct reading of the platform.
2. **Non-standalone (`standalone = false`).** The app is companion-only and read-only for card data;
   without a paired phone it can never obtain cards, so advertising standalone operation would be
   false. Consequence to accept: Play surfaces it only to users with a compatible paired phone — which
   is precisely the addressable audience.
3. **`applicationId` identical to the phone app, no suffix.** Platform-mandated. Explicitly overrides
   the instinct carried over from `targets/watch/expo-target.config.js`'s `bundleIdentifier: '.watch'`.
4. **The Wear OS APK gets its own `versionCode` band, `2_000_000`.** Story 16.7 established
   `PRODUCTION_VERSION_CODE_OFFSET = 1_000_000` for the phone's production band, leaving beta at the
   bare run number. A third independent counter needs a third band, and the watch APK's `versionCode`
   is set **in `watch-android`'s own Gradle build, not by `app.config.ts`** — the two projects share
   nothing. Document the band in the README next to a pointer to `app.config.ts` so the whole scheme is
   discoverable from either side.
5. **Add a path-filtered CI build job now, not later** — `watch-android/**` triggers
   `./gradlew assembleDebug`. Rationale: the phone app's Android surface already has no telemetry, and
   an uncompiled module rots silently. Keep it off the phone app's critical path via path filtering, as
   `chromatic.yml` does. If the Gradle setup proves slow enough to hurt, downgrade to a nightly and say
   so in the README — but do not ship Epic 10's foundation with nothing compiling it.
6. **No Room dependency in this story.** 10-5 owns the schema; an unused ORM invites out-of-scope
   invention.

### Debug Log References

Findings worth keeping, each established by running something rather than by reasoning about it:

1. **AGP 9.3.1 bundles KGP 2.2.10, but the Compose compiler plugin's version wins.** Declaring
   Kotlin 2.4.10 was verified to actually take effect, not silently fall back: the Kotlin daemon's
   compiler classpath shows `kotlin-compiler-embeddable-2.4.10.jar` and every other `kotlin-*` jar
   at 2.4.10, so there is no version skew between AGP's built-in Kotlin and the Compose compiler.
2. **`jvmTarget` is deliberately absent** from the build file. AGP's built-in Kotlin defaults it to
   `compileOptions.targetCompatibility`. Verified rather than trusted: `javap -verbose` on the
   compiled `MainActivity.class` reports **major version 61** (Java 17), and the class comes from
   `build/intermediates/built_in_kotlinc/...`, which also confirms built-in Kotlin did the compiling.

### Completion Notes List

- `watch-android/` is a standalone Gradle project with its own wrapper, version catalogue and
  `settings.gradle.kts`. **No Expo config plugin exists or was needed** — and this is stronger than
  the story anticipated: **AGP 9.0 removed embedded-Wear-app support outright** (the `wearApp`
  configurations are gone), so embedding is not merely unnecessary, it is unsupported. Nothing was
  written into `android/`, and `app.json` / `app.config.ts` / `targets/**` / `watch-ios/**` /
  `jest.config.js` / `package.json` were all left untouched.
- **No `org.jetbrains.kotlin.android` plugin** appears anywhere: AGP 9 ships built-in Kotlin and
  enables it by default. Only `com.android.application` and the Compose compiler plugin are applied.
- Sources live in `src/main/kotlin` (not `src/main/java`); confirmed picked up by built-in Kotlin.
- `versionCode` implements Open Decision 4's `2_000_000` band, read from a **`WEAR_VERSION_CODE`** env
  var — deliberately a different name from the phone's `ANDROID_VERSION_CODE` so a Wear build can
  never silently inherit the phone's counter. Read via `providers.environmentVariable` rather than
  `System.getenv` so it is a tracked configuration-cache input.
- **The counter fails loudly on a present-but-unusable value** (QA round 1, finding 3). Absent → the
  bare band, which is the local-build case. Empty, `0`, negative or non-numeric → the build fails,
  because falling back would emit a plausible-looking `versionCode` indistinguishable from a genuine
  first upload — the exact Story 16.7 failure, merely deferred to Play-upload time. An unset GitHub
  Actions variable interpolates to the empty string, so that case matters in practice. The sum is
  computed in `Long` and checked against Play's `2_100_000_000` ceiling before narrowing to `Int`, so
  a large counter cannot overflow into a negative `versionCode`. Verified by running each case:
  unset → `2000000`; `42` → `2000042`; `abc`, `""`, `-5`, `0` → `BUILD FAILED` with the explanatory
  message.
- **Release path was exercised on the final configuration** (QA round 1, finding 1): `assembleRelease`
  succeeds with R8 minification and resource shrinking (unsigned, as AC9 requires). It had first been
  run against the earlier Kotlin 2.2.10 pin and then wiped by a `clean` during the 2.4.10 evaluation,
  so the original claim was true-when-made but stale for the shipped config. Re-run and now backed by
  artifacts: `app/build/outputs/apk/release/app-release-unsigned.apk` plus an R8
  `outputs/mapping/release/mapping.txt`, and the release APK badges `versionCode='2000000'`.
- **Scope additions, both small and both flagged:** a launcher icon (the app would otherwise show the
  default Android robot in the Wear launcher) derived from the repo's existing
  `assets/adaptive-icon.png` rather than invented, and `data_extraction_rules.xml` to close the
  `allowBackup` deprecation on Android 12+. The icon is a **copy with no sync gate** — recorded under
  README § Known gaps.
- **Lint is clean except one warning left deliberately visible**: `MonochromeLauncherIcon`. Silencing
  it would hide a real gap (no themed icon on Android 13+), and fixing it needs a flat silhouette
  design asset that does not exist in this repo. Every suppression in `app/lint.xml` carries its
  reasoning; `GradleDependency` and `NewerVersionAvailable` are off because they are time- and
  network-dependent and make a lint run non-reproducible. **This count is post-re-run** (QA round 1,
  finding 2): the `DataExtractionRules` suppression had been added _after_ the previous `lintDebug`,
  so the report on disk still showed 2 warnings and the claim was unverified at the time it was
  written. `lintDebug` was re-run against the final tree and now genuinely reports 0 errors and this
  one warning.
- **`compileSdk` stayed at 36** although AGP 9.3 supports 37 and lint suggested it: 36 is what the
  phone app's Expo SDK compiles against and what CI runners provide, so 37 would mean provisioning a
  platform everywhere for no current benefit.
- AC8 honesty: the new CI job compiles and nothing more. The README states explicitly that no unit
  tests, no lint and no device run happen in CI, so the job's existence cannot be mistaken for
  broader coverage.
