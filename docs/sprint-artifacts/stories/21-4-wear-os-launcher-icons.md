# Story 21.4: Wear OS launcher icons — and the background colour that silently stopped matching

Status: ready-for-dev

Epic: 21 — Cardì Rebrand — Native Identity

> **⚠️ THERE IS A LIVE DRIFT BUG HERE, not just a stale icon.**
> `watch-android/app/src/main/res/values/colors.xml` declares
> `<color name="ic_launcher_background">#FFFFFFFF</color>` with the comment _"Matches app.json ->
> expo.android.adaptiveIcon.backgroundColor."_ **It does not.** `app.json` now reads `#181824`,
> changed by the Cardì rebrand in `f293c7f` (2026-09-13). The Wear background is still opaque
> white and the comment is a lie. Fix the value and the comment together.
>
> **⚠️ TWO README CLAIMS ARE NOW STALE and would mislead an implementer.**
> `watch-android/README.md` says a monochrome launcher icon needs _"a flat silhouette asset that
> does not exist in this repo"_. It exists — `assets/adaptive-icon-monochrome.png`, generated by
> Story 20.4. And it says the mipmaps are _"a faithful downscale of `assets/adaptive-icon.png`"_,
> which was true when written and is not now.
>
> **⛔ SEQUENCE AFTER 21.3.** Both stories extend `scripts/build-brand-icons.mjs`. The collision is
> **additive** — each appends artefacts to the same array — so it is a trivial rebase, not a
> semantic conflict. Land 21.3 first.
>
> **✅ THIS STORY DOES NOT DEPEND ON 21.2.** `adaptiveIcon.backgroundColor` is already `#181824`,
> so the value this story must match is stable today and does not wait on the colour migration.

## Story

As a Wear OS user,
I want the watch app to carry the Cardì mark,
so that the identity is consistent across every device the app runs on.

## Story context

`watch-android` is a **standalone Gradle project**, and its README states the constraint plainly:
it _"cannot reach into the JS app's assets without giving up being self-contained"_. So the
launcher icon is a **hand-copied PNG set**, and nothing keeps it in sync. The phone icon changed on
2026-09-13; these did not. Git confirms it: the only commit touching these mipmaps is `f56023c`
(2026-08-03), an ancestor of the rebrand.

### What exists today (verified)

Four density buckets, no `mdpi`, no `anydpi` without the v26 qualifier:

| path                                        | size      |
| ------------------------------------------- | --------- |
| `mipmap-hdpi/ic_launcher_foreground.png`    | 162² RGBA |
| `mipmap-xhdpi/ic_launcher_foreground.png`   | 216² RGBA |
| `mipmap-xxhdpi/ic_launcher_foreground.png`  | 324² RGBA |
| `mipmap-xxxhdpi/ic_launcher_foreground.png` | 432² RGBA |

All four carry the **old blue wallet drawing** (verified visually).

`mipmap-anydpi-v26/ic_launcher.xml` declares exactly two layers — `@color/ic_launcher_background`
and `@mipmap/ic_launcher_foreground`. **There is no `<monochrome>` element**, and
**`ic_launcher_round.xml` does not exist**; the manifest declares only `android:icon`, no
`android:roundIcon`. `minSdk` is 30, so the v26-qualified resource always matches and no legacy
square fallback is needed.

`watch-android/app/lint.xml` deliberately leaves `MonochromeLauncherIcon` **unsuppressed** so the
missing themed icon stays visible. `build.gradle.kts` contains no icon reference at all.

## Acceptance Criteria

- **AC1 — `ic_launcher_foreground.png` is generated for all four densities** (162/216/324/432) by
  `scripts/build-brand-icons.mjs`, carrying the Cardì mark. Hand-copying is what produced this
  drift; the story's point is to end it.
- **AC2 — `colors.xml`'s `ic_launcher_background` becomes `#FF181824`** (opaque ink), matching
  `app.json`'s `adaptiveIcon.backgroundColor`, **and its comment is corrected** so it no longer
  asserts a match that has to be taken on trust.
- **AC3 — `mipmap-anydpi-v26/ic_launcher.xml` declares the correct foreground and background**, and
  its explanatory comment is updated — it currently says the layers are "a faithful copy of the
  phone app's declared Android icon", which will again be true, but by generation rather than by
  copying. Say which.
- **AC4 — A `<monochrome>` layer is added, or its absence is re-justified.** The blocking asset now
  exists (`assets/adaptive-icon-monochrome.png`). If monochrome is added, the `MonochromeLauncherIcon`
  lint suppression question is settled in the same change. If it is deliberately deferred, the
  README claim that the asset "does not exist" is corrected regardless.
- **AC5 — The mark is verified against Wear OS's CIRCULAR launcher mask** and at the smallest
  launcher size on a 384 px round device.
- **AC6 — Rendering is verified on BOTH a round and a square AVD**, since Wear OS ships both.
  Screenshots attached.
- **AC7 — `yarn icons:check` covers the four new artefacts**, so this set can never silently drift
  from the phone's again. This is the acceptance criterion that actually fixes the bug; AC1 only
  fixes today's symptom.
- **AC8 — The two stale `watch-android/README.md` claims are corrected** — the monochrome asset and
  the hand-copy provenance.

## Dev Notes

### Guardrails

- **`rotate(35)` ✓ / `rotate(-35)` ✗** — a negative rotation produces an acute (Story 20.3).
- **Do not make `watch-android` read the JS app's assets.** Its self-containment is deliberate and
  documented. The generator writes _into_ `watch-android/`; the Gradle project still reads only its
  own `res/`.
- `wear-os-build.yml` is path-filtered to `watch-android/**`, so it will run for this change — but
  it only builds and unit-tests. **No CI job validates these icons**; AC7 is what changes that, via
  `ci-quality-gates.yml`, which is not path-filtered.
- Ships in the single rebrand release (Story 21.7), even though the Wear APK releases on its own
  track — the identity must not be split across two releases.

### Testing

`yarn icons:check`, `./gradlew :app:testDebugUnitTest` in `watch-android/`, `yarn format:check`.
AC5 and AC6 are emulator work.
